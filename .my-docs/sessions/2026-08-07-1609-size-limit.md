# 세션 요약: 요청 크기 상한 조사

- **날짜**: 2026-08-07 16:09
- **프로젝트**: kirocc (Anthropic Messages API → Kiro 백엔드 프록시)
- **브랜치**: main

Kiro가 `CONTENT_LENGTH_EXCEEDS_THRESHOLD`(400)로 요청을 거부하는 현상을 조사했다.
원인 규명이 주 작업이고, 코드 변경은 진단 수단 추가에 그쳤다. 근본 대응은 미결.

## 수행 작업

### 1. launchd 에이전트에 환경변수 전달 (커밋 `964b824`)

`-debug`를 켤 방법이 없었다. launchd는 에이전트에 셸 환경을 물려주지 않아
`export KIROCC_DEBUG=true` 후 `make service-install`을 해도 서비스에 전달되지
않는다. plist 템플릿에 `@EXTRA_ENV@` 자리를 만들고 `render_plist`가 현재 셸의
`KIROCC_*` 10개를 채우게 했다.

전체 통과가 아니라 명시적 열거로 했다 — 셸에 남은 변수가 서비스 동작을 조용히
바꾸면 추적이 어렵다.

검증 중 버그 2개를 잡았다. 플레이스홀더를 `</dict>`와 같은 줄에 두면 awk가 닫는
태그까지 지워 plist가 깨졌고, `KIROCC_MODEL_MAPPINGS`는 JSON이라 `&`나 `<`가
들어가면 launchd가 파싱을 거부해 에이전트가 조용히 죽는다. 후자는 XML 이스케이프로
해결. 4개 경우(없음/하나/여러개/특수문자) 모두 `plutil -lint` 통과 확인.

사용법: `KIROCC_DEBUG=true make service-install`

### 2. 400 거부 시 요청 캡처 (커밋 `964b824`)

캡처가 `retryReasonEmptyVisibleEndTurn` 경로에만 걸려 있어(`execute.go`의 응답 처리
직후 분기) 400으로 거부된 요청은 무엇을 보냈는지 기록이 없었다.
`GenerateAssistantResponse` 실패 경로에서도 `logCapture`를 호출하게 했다.

클라이언트 요청 크기는 대체 지표가 못 된다. Kiro 히스토리에는 `images` 필드가
없어(`kiroproto/types.go:163`) kirocc가 받은 이미지를 전부 떨어뜨리고 재생 창만큼만
현재 메시지에 되붙이므로, 나가는 요청은 받은 것과 크기가 다르다. 그래서
`upstream_body_len` / `image_count` / `image_bytes` / `history_len`을 캡처에 추가했다.

로그에 남기는 본문은 64 KiB로 절단했다. 거부된 요청은 수 MB가 되는데 크기는 위
필드가 답하고 본문은 형태만 보면 되므로, 전체를 남기면 주변 로그를 묻고 로테이션만
소모한다.

### 3. 원인 규명 — 가설 2개 반증, 1개 확인 (코드 변경 없음)

**반증 1: 세션 전체 토큰 수가 아니다.** 화면에 76만 토큰(76%)이 보여 컨텍스트
초과를 의심했지만, 로그에 138만 토큰 성공 기록이 있었고(8/6 09:47) 76만 요청
자체도 200이었다. `/compact` 권고는 근거가 없어 철회.

**반증 2: 총 바이트 크기 단독이 아니다.** 실측으로 상한을 쟀다 — 히스토리 없는
단일 메시지는 **5.2 MiB 통과 / 5.3 MiB 실패**. 그런데 실패한 실제 요청은
`upstream_body_len = 2,389,137`(2.28 MiB)였다. 절반도 안 되는 크기에서 거부됐다.

**반증 3: 이미지도 아니다.** 캡처의 `image_count = 0`. 사용자가 "2턴 동안 이미지
붙인 적 없다"고 한 것이 맞았고, 클라이언트가 보낸 4.28 MiB에 이미지 7장(2.38 MiB,
55%)이 있었지만 재생 창을 벗어나 전부 탈락했다. 따라서 "4MB 넘으면 이미지 떨구기"
방안은 이 문제에 무효 — 떨굴 이미지가 없다.

**확인: 히스토리가 있으면 상한이 급격히 낮아진다.**

| 히스토리 | 총 바이트 | 결과 |
|---|---|---|
| 없음 | 5.2 MiB | 통과 |
| 없음 | 5.3 MiB | 실패 |
| 1,480 엔트리 | 2.31 MiB | 통과 |
| 1,480 엔트리 | 2.88 MiB | **실패** |

개수 자체는 원인이 아니다 — 2,001 메시지를 0.45 MiB로 보내면 통과한다. 총 바이트
단독도 아니다 — 같은 2.3 MiB가 히스토리 유무로 갈린다. 즉 Kiro는 히스토리를 별도로
세는 예산을 갖고 있고, 엔트리당 고정 오버헤드가 붙는 형태로 보인다(1,480 엔트리에서
약 2.3 MiB 소실 → 엔트리당 ~1.5 KB). 실패 사례 2.28 MiB는 그 경계 바로 아래였고
대화가 자라며 넘어갔다.

**추가 축: 도구 스키마.** 사용자가 MCP를 끄자 통과했다. 실패 캡처에
`tool_count = 151`이 있었으므로 도구 정의도 예산을 먹는다. 예산은 히스토리 +
현재 메시지 + 도구 정의의 합으로 보이며, 총 바이트만으로는 예측되지 않는다.

### 4. `body read idle timeout` 원인 (별건, 코드 변경 없음)

별도로 발생한 stream error를 추적했다. 업스트림이 3분 36초 침묵해
`defaultBodyReadIdleTimeout = 180s`(`kiroclient/client.go:68`) 가드가 발동했다.
`reading prelude`이므로 응답이 시작조차 안 된 상태.

"어떻게 풀렸나"의 답: kirocc 재시도가 아니다. 같은 trace에 `<--` 응답 로그가 없고,
4초 앞서 **다른 trace**가 시작되어 15초 만에 200을 받았다. Claude Code가 별도로
재요청한 것이다. kirocc의 retry-once는 403/429/5xx/빈 응답만 대상이고 idle timeout은
상태 코드가 없어 분류되지 않는다. 로그 전체에서 2건(7/28, 8/5)뿐이라 빈도는 낮다.

### 5. my-wrap 스킬 자동 판단화 (레포 외부)

`~/.claude/skills/my-wrap/SKILL.md`. append 여부를 매번 묻던 것을 스스로 판단하게
고쳤다. 기존 기준이 "같은 서비스/레포"였는데 한 레포에서 여러 무관한 작업을 하는 게
정상이라 거의 항상 후보가 잡혔다. 기준을 **인과성**으로 바꿨다 — 그 세션의 남은
작업을 처리했거나 그 세션이 만든 것에 반응했으면 append, 아니면 새 파일. 모호하면
새 파일로 기울인다(잘못된 append는 무관한 문서에 묻혀 찾지 못하지만, 흩어진 새
파일은 나중에 합칠 수 있다). `--new` 플래그 추가. 실제 판단 3건에 대입해 전부 일치
확인.

      다른 에러 경로(429/5xx/`STALE_CONVERSATION`/스트림 이벤트)는 건드리지 않는다
- [ ] 디버그 끄기 — 고치기 전까지만 켜두기로 했다. 로그가 1분에 10MB씩 쌓이고
      `-log-max-backups` 기본 5라 60MB만 유지된다. 계속 켤 거면
      `KIROCC_LOG_MAX_SIZE=100 KIROCC_LOG_MAX_BACKUPS=20` 권장
- [ ] 예방 경고 검토 — kirocc는 매 요청 크기를 알므로 예산 80% 같은 시점에 경고할
      수 있다. 아직 compact가 통과하는 시점에 조치하게 하는 것이 목적. 다만 임계값을
      정하려면 예산 공식을 더 재야 한다(지금은 "1,480 엔트리에서 2.9 MiB" 한 점만 안다)
- [ ] 히스토리 절삭은 **만들지 않기로** 결론 — 예산 공식을 모르는 상태에서 맥락을
      조용히 버리는 코드는 위험하고, 수동 탈출 경로(MCP 끄고 `/compact` 후 재활성)가
      확인되었으므로 필요도 없다
